# 动态日程接力说明

实现日期：2026-11-14。基于包含 `75cc951` 的本地分支 `feat/dynamic-npc-schedules`。只增加日程能力，保留原有社交图、记忆算法、地图寻路与对话播放规则。

## 1. 计划如何产生

HTTP 服务由 `SocialService` 装配 `DynamicSchedule`，`Scheduler.tick()` 在会面与自然相遇检测前推进活动状态。`World` 只保存实际地点和锁定的 `activity_targets`，不依赖调度器；CLI 的 `GameService` 继续沿用原固定日程。

- **基础习惯**：人格卡 `schedule` 保持原样。没有其它安排时，建立基础活动；已经上路则保留该目的地，跨过作息时段或午夜都不会自动改道。抵达后至少停留一段时间，才回到最新基础安排。
- **每日变化**：每人每天默认增加两项机会，分别在9:00～10:30和14:00～15:30出发。使用角色名与游戏日生成稳定种子，重启不会重新随机。按身份、性格、目标、本人近期活跃记忆和好友关系加权选择活动；同日的两项类型不同。没有适用活动时继续基础习惯，没有每日到智信馆的配额。
- **记忆响应**：每5现实秒检查本人最近6条活跃记忆；研究资料、图书、文献或运动相关经历可产生一次柔性安排。已遗忘记忆不参与。通知已经产生安排时，不再将同一条观察记忆当作第二个邀约。带明确钟点、取消或否定的记忆不直接当成即时出发指令。
- **关系响应**：达到好友阈值的关系可产生讨论邀约。复用原会面队列，等待双方空闲、实际赴约和冷却结束；没有新建一套对话系统。日程不会把对方的记忆、人格秘密或私下收到的事件传给发起人。
- **可选模型计划**：规则计划先立即生效，后台再通过 `AgentRuntime.plan_day()` → `llm.chat_json()` 生成今天剩余时间的1～3项建议。输入为本人公开人格、基础日程、本人活跃记忆、本人收到的事件、本人关系及允许地点。通过校验后只替换尚未开始的每日规则机会，不覆盖进行中的活动、手动指派或事件安排。

活动目录在 `backend/activity_catalog.py`：科研使用济事楼实验室/机房，组会使用四楼讲座教室，资料查询使用智信馆图书分馆，教学交流使用智信馆教室，运动使用智信馆健身休息区，教务工作使用机房/档案资料室，好友讨论使用图书分馆/茶水间。角色权重不同，学生不会抽到教务专属工作。

## 2. 事件和知情范围

继续使用 `POST /social/event`（或原 `/debug/event`），例如：

```json
{"text":"明天10:00到四楼讲座教室参加组会","participants":["陈卷","周冲"]}
```

只有 `participants` 中的角色获得该观察记忆和安排；这里表示已经明确收到通知，并非把发布公告等同于全员知情。API仍异步记录事件，返回 `ok` 表示已排队。`World.inject_event()` 直接产生的事件也会在下一次上下文扫描中被处理。

规则识别组会/讲座/报告会、图书/查资料/文献/研究问题/讨论项目、上课/课程/教室/考试、运动/健身。没有匹配的群体事件继续使用原来的会面队列逻辑。相同事件不会重复建活动；默认每人每天最多4项事件响应、1项记忆响应。

带 `HH:MM` 或“明天”的通知作为期望钟点，默认提前180游戏分钟准备出发，最早不早于收到通知时刻。明确的智信馆教室编号（例如 `n219`、`zx2_n219`）优先选对应房间；没有指定房间时，同一条通知的接收者选择相同的有效房间。已经过去的明确约定不会重新创建行程。“取消组会”“取消上课”等只取消实际收到取消通知的角色的同类事件安排。已经开始处理的会面对话不强制中断。

这是有限关键词/钟点规则，不是完整的自然语言日历。当前不解析星期、重复课程、任意日期、复杂否定或地点变更。通知钟点是尽力赴约的参考，实际行走可能迟到；不会为了准点传送或反复改道。需要严格课堂截止时间时，可按活动类型增加专门的截止策略。

## 3. 状态、冲突与时间

基本生命周期：`scheduled`（尚未开始）→ `travelling`（正在前往）→ `active`（已到达/活动中）→ `completed`。阻塞时显示 `waiting`，保留原来的行走或停留阶段；其它终态为 `cancelled`、`timed_out`。

优先处理已经占用角色的对话/反思任务，之后依次为手动指派、已有会面队列、明确事件（70）、相关记忆（40）、每日规则/模型/好友机会（20）、基础作息（0）。数值用于活动之间的仲裁；会面和忙碌通过已有服务的占用机制协调。

- 普通每日机会不会打断尚未走完的低优先级行程；事件和手动指派可以替换较低优先级活动。同等优先级按先安排的顺序等待。
- `POST /world/goto` 建立手动活动，忙碌时先等待；关联双方的会面暂缓。手动活动抵达、短暂停留后恢复日程，取消/超时也会释放占用，不再依靠固定作息翻段使指派失效。
- 会面临时占用普通活动时暂停活动计时。会面后如已离开原地点，先走回原活动地点并重新确认到达，再开始该次停留。
- 自然相遇继续工作；手动/明确事件活动不会被普通自然社交抢占，已在行走时不再临时发起远处访友。普通活动中实际同室相遇仍可聊天，处理结束后恢复活动；气泡本身不占用角色。
- 前端没有位置上报时显示等待，行走/停留预算都暂停。地图转场依旧使用现有路线和落脚点，后端不会修改角色实际坐标或传送。

`/world/report` 增加可选 `arrived` 和 `activity_id`：经过房间上报 `arrived:false`，完整行程结束才上报 `true`；编号让同房间新活动也重新确认，旧活动的延迟回包不能启动新活动。两字段均可省略，兼容原客户端的房间粒度上报。实际地点仍会更新，活动是否开始另外校验。

**默认时钟保持现实1秒=游戏10分钟，1小时/4小时/3天快进和原速恢复均保留。** 行走预算及最短停留按 `speed / SOCIAL.speed` 归一化，与前端移动倍率一致；游戏停留时长只从实际到达后累计，暂停、掉线和角色占用期间不累计。默认可选活动停留180游戏分钟，同时至少达到原速下12现实秒；原速约18现实秒，六倍速约3现实秒。原速下行走预算300现实秒；未出发活动过期窗口720游戏分钟。这些宽限用于应对游戏时钟比物理行走快得多的情况。

## 4. 参数、存储与扩展

关键参数集中于 `backend/config.py` 的 `ACTIVITY`：

- `enabled`：动态调度总开关；关闭时沿用旧日程与旧指派。
- `daily_optional_count`、`dwell_minutes`、`min_stay_seconds`：每日机会数量与到达后停留。
- `travel_timeout_seconds`、`pending_expiry_minutes`、`appointment_lead_minutes`：行走、待出发过期、赴约提前量。
- `context_scan_seconds`、`memory_reactions_per_day`、`event_reactions_per_day`、`friend_threshold`：响应频率和关系门槛。
- `model_enabled`、`model_interval_seconds`、`model_timeout_seconds`、`model_result_deadline_seconds`：模型开关、全局请求间隔、单次传输超时、结果采用期限。
- `history_days`：完成记录等历史保留窗口，默认3个游戏日；未完成行程继续保留。

每NPC每游戏日最多请求一次模型计划；全局最多一个在途规划请求，两次提交至少间隔8现实秒。没有key不提交。单次模型传输限时8秒且关闭SDK的额外网络重试，保留原JSON/空正文重试逻辑；12现实秒后结果不再采用，规则计划持续运行，旧请求结束前也不开新规划请求。其它对话请求的原超时设置不变。

校验包括：活动类型、角色可用地点组合、真实房间、当天尚未过去的出发时刻、30～360游戏分钟的有限时长、最多3项、计划内部不重叠、访友对象属于本人好友、所声明的事件/记忆/关系依据确实存在。模型不能指定其它NPC的目标。整个方案先校验再写入；超时、空结果、错误JSON或无效活动一律保留规则兜底。公开原因使用服务端简短模板，不展示原始私密记忆或模型提示词。

SQLite新增 `npc_activities`、`npc_plan_days`、`npc_plan_signals`，保留活动、每日模型尝试状态及去重标记。重要状态变化及正常关闭时保存进度；异常退出可能丢失最近一个阶段内的部分计时。重启后目标继续下发，实际位置仍由新前端上报，未完成好友活动重新进入原会面队列。新增记录的旧终态和去重标记按保留窗口清理，原有记忆/检查点表不在此处改动。

增加活动时修改 `CATALOG` 的标题、有效房间和角色权重，并同步 `PlannedActivity.kind`、动机模板及必要的通知关键词。新增房间仍按地图交接重建manifest和导航网格，再将规范 `map_id/room_id` 放入活动目录，不要添加“假地点”或后台传送。新增角色角色类别不同于student/advisor/staff时，需要为该类别补活动权重，否则固定日程继续兜底。

## 5. 观察与调试

活动信息统一在“社交观察 → 角色资料”查看，不再额外显示右上角固定日程窗口。选中角色后明确标注“当前活动”“活动状态”“安排依据”“行程说明”和“目的地”，抵达后仍保留目的地标签。公开人格接口的原字段白名单不变。

社交观察展开后，可按住标题栏“拖动此处移动”拖到合适位置，边缘限制保证标题仍可操作；收起后再展开保留本次运行中的位置，切换页签或调整窗口大小会按可用空间修正位置。面板内也有“收起”按钮。点击地图上的人物或姓名，会跟随该NPC、展开社交观察并切到对应角色资料；镜头缩放和跨楼层后跟随继续有效。面板内的按钮、下拉框、滚动和拖动不会点中背后的NPC，地图试走界面也不会触发NPC选择。原有空格切换跟随、Esc取消跟随保留。

基础安排显示为“基础作息”，行走显示“正在前往目的地”，抵达显示“已到达，正在进行活动”。数据库里已保存的旧文案在查询时自动转换，不需要清空数据，也不改变行程、状态或计时。

`GET /world` 的每名NPC新增 `activity`，保留原目标字段。`GET /npcs/{name}/activities` 可查当前描述和最近20项安排；`POST /npcs/{name}/activities/{id}/cancel` 取消指定活动，已经开始处理的会面返回409。活动变化使用已有WebSocket事件流的 `activity_changed`，常规世界快照继续同步显示。

无模型密钥和无后端是两种情况：前者由本系统规则/基础日程继续驱动真实行走；后者仍显示原有Godot本地演示，不在此轮改写本地随机演示机制。

## 6. 验证与待人工体验

在仓库根目录运行：

```powershell
.\.venv\Scripts\python.exe -X utf8 -B -m unittest discover -s tests -v
$env:GODOT_EXE=(Resolve-Path '..\tools\godot\Godot_v4.5.2-stable_win64_console.exe').Path
.\.venv\Scripts\python.exe -X utf8 -B tests/run_dynamic_schedule_smoke.py
```

新增后端测试使用模拟模型和临时数据库，覆盖事件知情范围、延后扫描、人格/身份差异、三图活动机会、本人记忆与隐私、无模型、非法房间/时间/关系/重叠计划、后台模型调用链与频率、超时丢弃、行走锁定、跨日/六倍速、到达确认与旧包、忙碌/手动/会面冲突、掉线和超时、正常重启及好友会面重新排队。

`run_dynamic_schedule_smoke.py` 启动临时后端和随机端口，以真实Godot的ApiClient接收事件生成的图书分馆目标，周冲从济事楼沿现有跨馆路线实际行走，再通过真实HTTP上报，验证进入活动中，并核对角色资料中的活动标签及重复窗口已移除。测试专用时钟跳跃用于证明跨午夜目标保持，不是生产快进实现。外层有90现实秒限时；固定帧率测试中关闭引擎计时的HTTP超时，避免加速物理帧误触发网络超时。设置 `ROAM_DYNAMIC_PREVIEW` 为PNG绝对路径可执行实际图形渲染并输出截图；不设置则无窗口测试。

本轮后端共50项测试通过（原有30项、新增20项）。Godot角色资料页、社交界面、连续时钟/移动倍率、试走西楼梯双向转场、真实WebSocket及校园40房间/跨层/跨馆/门扇回归通过；动态计划的真实HTTP导航闭环通过，实际图形渲染截图已检查角色资料的字段与布局。忙碌时忽略的上报不会写入前端确认缓存，解除占用后可重报。

交互复测入口：`tests/check_observer_interaction.gd`。使用Godot真实输入分发覆盖标题拖动、屏幕边界、展开位置保留、UI遮挡、点击不同人物联动资料、镜头缩放和跨层跟随，以及原有取消/切换跟随。

尚未调用真实模型网关；模型输出质量及长时间运行时的活动分布需人工体验。建议先无key观察数日，再依次发送“去图书分馆查资料”“明天10:00组会”“取消组会”，并在途中安排会面或手动指派，检查各角色等待与恢复是否符合预期。不要将自动化使用的替身模型结果当成真实模型效果证明。
