# 校园地图规范

## 当前三张地图的家具与通行规则

济事楼三楼、济事楼四楼和智信馆二楼均按以下约定维护。每个房间及连通走廊的地板各占一个 `room_*` 层。桌子下面仍保留房间地板，家具的占地单独标在障碍层。

| 物件 | 应放图层及效果 |
| --- | --- |
| 墙、隔断 | 放在 `wall`，门洞留给 `door`。关门挡人、开门通行。 |
| 桌体、讲台、椅座、沙发、柜子、落地花盆、健身器械 | 将角色不能站立的占地放在 `obstacle`。已有的柜体层 `obstacle_storage` 也挡人。长桌包括桌面正下方，盆栽至少挡住花盆底座。 |
| 地毯、地面纹样、墙画、桌面的书本等小物 | 放在 `zhuangshi*` 装饰层，可以走过地毯。书本叠在桌面，由桌体挡人。墙画贴墙。 |
| 门、楼梯、可操作的设备 | 分别放在 `door`、`stair`、`interactable*`，并在楼层的 `manifest.json` 登记。落地设备仍需要实体占地。 |

摆放时给人留出进门、绕桌、靠近交互点的路线。走廊中央可以铺地毯。盆栽、立式摆件靠墙或角落，花盆底座应挡人。高出底座的枝叶可作为装饰，允许人物从旁边擦过。

三份可编辑的 Sprite Fusion 工程统一放在仓库的 `map_sources/`。换图层、保存源图、重建 Godot 楼层和提交的具体步骤见[《校园地图改图交接》](../map_sources/README.md)。

若要检查某一格，打开 `frontend/assets/map/<楼层>/grid.json`。在 `obstacle` 中从 0 开始数，第 `y` 行第 `x` 列为 `1` 时挡住，为 `0` 时静态可走。试走还会检查门的开关。重建命令同时更新这份网格、Godot 图层和瓦片碰撞形状。只在 Godot 编辑器查看归层，可以展开楼层的 `Map.tscn`，用小眼睛依次隐藏 `obstacle` 和 `zhuangshi`。

## 1. 现状: 三个场景, 一张图

后端 `backend/world.py` 的 `AREAS` 定义了**三个场景**共 10 个语义区域:

| 场景 | 语义区域 (AREAS id) |
|---|---|
| 纪事楼 3F | `j3_lab` 实验室 · `j3_pantry` 茶水间 · `j3_wc` 洗手间 |
| 纪事楼 4F | `j4_lab` 实验室 · `j4_meeting` 会议室 · `j4_wc` 洗手间 |

里的 `GRID_OF` 映射表: 把 4F/智信馆的语义区域**投影**到 3F 的对应房间，
让任何日程在前端都有路可走（答辩话术: "单楼层复刻 + 多楼层语义"）。

> M4 做真实跨楼层前必须补画另外两张图，走完全相同的提取管线

> 提示: 4F 与 3F 是同一栋楼，画 4F 时楼梯位置应与 3F 对齐（R08/R11/R13

## 2. 当前实现: 数据从哪来、怎么变成寻路网格

### 2.1 数据来源

网页绘图工具（导出 "Godot 工程"）→ 11 个文件:

```
frontend/assets/map/jishilou_floor3/
├── Map.tscn            # 场景根, 只做 7 个图层 .tscn 的实例化
├── guizi_0.tscn        # ── 7 个 TileMapLayer, 文件名编号=绘制顺序(z序)
├── zhuangzishangmian_1.tscn  # 桌上物
├── zhuangshi_2.tscn    # 装饰
├── wall_3.tscn         # 墙
├── louti_4.tscn        # 楼梯
├── ditan_5.tscn        # 地毯
├── ground_6.tscn       # 地板
├── tileset.tres        # 瓦片集(含每个瓦片的碰撞多边形, 文本格式)
├── tileset.png         # 瓦片图集 16x16
├── jishilou_floor3.json / map.zip  # 工具私有格式(我们不用)
```

关键认知: **这 7 个图层是渲染分层**(解决遮挡/绘制顺序), 不是逻辑分区。
"哪 500 格是实验室"这件事在数据里完全不存在。

### 2.2 提取管线 (`frontend/tools/extract_map_data.py`)

从上述场景文件反演出逻辑数据, 四步:

1. **墙 = `wall_3` 图层本体**。障碍物单独看家具层不可靠(有的瓦片有碰撞
   有的没有, 碰撞定义藏在 `tileset.tres` 的 physics polygon 子资源里,
   需正则抠出)。最终障碍 = wall_3 ∪ tileset 声明碰撞的家具瓦片。
2. **门 = 墙线上的缺口**, 且必须同时满足: 宽度 1~3 格 + 缺口两侧都是真墙
   (过滤家具缝隙)。⚠️ 初版按"障碍物邻接"判门, 2 格宽门漏检, 洪水填充时
   R01 一口气吞掉全图 2196 格——这是本管线最大的一次翻车, 教训: 门必须
   以墙的本体定义, 不能以"周围有什么"推断。
3. **洪水填充定区域**: 门格临时封闭后, 对非障碍格做连通块标记,
   连通块 = 房间; 小于 `MIN_REGION_TILES=8` 格的碎片丢弃。
   产出 13 个区域 / 77 个门。
4. **孤立格 BFS 归并**: 被墙围死的零星格并入相邻区域。

### 2.3 两层设计: 自动层 + 语义层 (核心妥协)

纯几何无法判语义(哪块是机房哪块是走廊? 下半部房间的 4~9 格开放门洞
本来就没有门, 几何上无法封住)。所以:

| 层 | 谁负责 | 内容 |
|---|---|---|
| 自动层 | `extract_map_data.py` | 墙/门/连通块 → R01~R13 编号稳定 |
| 语义层 | `room_overrides.json` (人工) | `extra_walls`: 虚拟墙封闭无门的宽门洞(当前 3 处 16 格, 留 2 格当门); `renames`: 改房间名/类型 |

改 `room_overrides.json` 后**重跑提取器**即生效。当前区域名全部带
"(待定)"占位, 等后续同学修订。

### 2.4 产物与运行时

```
floor3_grid.json   # 寻路网格: tile_size=16, size=[133,70],
                   # obstacle('0'可走'1'障碍), room_grid(房间号矩阵)
rooms.json         # 13 区域元数据: id/name/type(room|corridor)/area_tiles/
                   # bbox/aspect/nav_point(导航点)/door_cells(门格)
_region_preview.txt# ASCII 预览图, 改 overrides 时对照
```

运行时 `frontend/scripts/game_data.gd`(autoload `Game`) 加载两份 JSON,
建 AStarGrid2D(4 邻接/曼哈顿/禁对角穿缝) + 房间查询
(`room_id_at` / `nav_world_of` / `random_world_in`)。

## 3. 踩过的坑与妥协一览 (补图同学重点读)

| # | 坑 | 当前的妥协 | 理想格式下 |
|---|---|---|---|
| 1 | 图层只有渲染分层, **无房间概念** | 洪水填充反演 + overrides 人工修语义 | `room_<id>` 分层, 填充逻辑整个删除 |
| 2 | **门无法从数据辨认**(门只是墙线缺口, 无 Door 实体; 宽门洞/家具缝隙/真门数据上一模一样) | 宽度≤3 + 两侧真墙过滤 + 虚拟墙人工补 | `door` 层显式标记, 零猜测 |
| 3 | `tile_map_data` 是 **PackedByteArray 二进制**, 无官方字节布局文档 | 逐 12 字节手动解包(坐标×2/source_id/atlas×2/alternative, int16) | 不受影响(仍需解包, 但已封装成函数) |
| 4 | 碰撞定义藏在 `tileset.tres` 文本的 sub_resource 里 | 正则抠 physics polygon | 不变 |
| 5 | 楼梯瓦片被装饰层覆盖 → 楼梯间被切碎成 R08/R11/R13 三块, stairwell 类型判定失败, **跨楼层连接无数据表达** | 接受现状, 楼梯间当普通房间; 跨楼靠 GRID_OF 投影 | `stair` 层带连接 meta, 真实跨层寻路 |
| 6 | 无出生点/导航点/POI | nav_point 按区域几何估算 | `spawn`/`interactable` 层显式标记 |
| 7 | 家具"有的挡人有的不挡", 数据上难以区分 | 只按 tileset 碰撞位判定, 桌上物可穿(观感瑕疵: NPC 可能走在桌面上) | `obstacle`/`deco` 分层, 表达即事实 |
| 8 | 工具自带伪造 uid → Godot 打开告警 | 无害, 编辑器保存一次生成正确缓存 | 不变 |
| 9 | 7 层数据分散在 7 个 .tscn | 正则遍历 `^[a-z]+_\d+.tscn` | 不变(或工具单文件导出) |

另一个纯工具链的坑(记录给后人): `rooms.json` 本身是 UTF-8 没问题,
但 Windows PowerShell 控制台按 GBK 显示会全乱码——**文件没错, 别被
终端显示骗了去"修"文件**。

## 4. 理想格式约定 (MAP_SPEC v1)

核心原则一句话: **渲染层为绘制顺序服务, 逻辑层为 gameplay 服务, 两者解耦。
图层命名即语义。**

### 4.1 图层命名约定

| 图层名 | 内容 | 程序行为 |
|---|---|---|
| `room_<id>` ×N | **地板按房间分图层**, 层名=房间 id (如 `room_lab`, `room_pantry`) | 图层名直接给出房间分区, **洪水填充/门检测/孤立格清理全部不需要** |
| `wall` | 唯一墙体层(含门窗洞) | 寻路障碍 |
| `door` | 每扇门一格标记(可附朝向) | 门列表直接可用; 宽门洞想当门就标, 不想就不标 |
| `interactable` | **可交互物品单独层**, 每件带 id: 白板/饮水机/打印机/电脑/马桶 | 运行时挂 Area2D/交互提示; M3 对话话题锚点("走到白板前讨论") |
| `stair` | 楼梯, 瓦片 meta 注明连接目标(哪层哪格) | 真实跨楼层寻路 |
| `spawn` | 出生点/导航点标记, 每房间至少一个 | roster 的 home / nav_point 直接引用, 不再几何估算 |
| `obstacle` | 带碰撞家具(柜子/桌体) | 障碍 |
| `deco` | 纯装饰(地毯/墙上贴画), 无碰撞 | 仅渲染 |
| 其余渲染层 | 保持原绘制顺序叠放即可 | 只看渲染 |

要点: `room_*` 分层不需要把房间地板拆散重画——在工具里按房间建图层、
把对应地板瓦片挪进去即可; 墙和家具维持整层。

### 4.2 manifest.json (楼层逻辑清单, 每张图一份)

房间名/类型/邻接这类**语义属性**放数据文件, 不放图层名(图层名只承担 id):

```json
{
  "map_id": "jishilou_3f",
  "tile_size": 16,
  "rooms": [
    { "id": "lab",   "name": "J3实验室", "type": "lab",
      "nav": "center", "tags": ["可触发组会"] },
    { "id": "pantry","name": "茶水间",   "type": "public" },
    { "id": "hall",  "name": "主走廊",   "type": "corridor",
      "vision": "range_10" }
  ],
  "interactables": [
    { "id": "whiteboard_lab", "item": "白板", "room": "lab" }
  ],
  "stairs": [ { "at": [84, 20], "to": "jishilou_4f", "at_to": [84, 20] } ]
}
```

- `type` 即后端视野规则(room=室内互见 / corridor=距离截断), 与 `world.py`
  的 kind(lab/office/public/facility) 语义对齐
- `vision` 允许房间级覆盖默认视野规则
- `rooms[].name` 随便改, 代码只认 `id`——和 R## 编号的设计一脉相承

### 4.3 收益对照 (这套约定能省掉什么)

| 现有组件 | 命运 |
|---|---|
| 洪水填充 + 门检测 + 孤立格清理 (extract 三大步) | **删除**——图层名即分区 |
| `room_overrides.json` (虚拟墙 + renames) | **删除**——门显式、名进 manifest |
| 77 门 / 3 处虚拟墙的人工核对 | 不再需要 |
| `extract_map_data.py` | 从"逆向推理器"缩成 ~100 行"格式转换器" |
| `nav_point` 几何估算 | 用 spawn 标记, 精确且语义化 |
| 跨楼层 GRID_OF 投影 | stair meta 支持真实寻路后删除 |

### 4.4 渐进路径 (不想换绘图工具时)

保持现有 7 个渲染层不动, 只**加一个不可见的"逻辑标记层"**: 用特殊瓦片
在图上标出——房间锚点(每房一格)、门格、POI、出生点。提取脚本优先读
标记层, 读到标记就跳过对应的反演步骤(填充/门猜测/导航点估算)。
改动成本一个下午, 表达力够 M3/M4 使用。这是**推荐的折中方案**。

## 5. 实施建议

1. **M4 前补画纪事楼 4F / 智信馆 4F 时, 直接按 §4.1 命名约定绘制**,
   并各配一份 manifest.json; 提取脚本加一个 `--spec v1` 分支走新路径。
2. 若工具不支持按房间分层, 退回 §4.4 逻辑标记层方案。
3. 新图的房间 id 建议直接用后端 AREAS 的语义 id (`j4_lab` 等),
   消灭 GRID_OF 映射表——后端 AREAS 与前端 rooms 两套 id 就统一了。
4. 现有纪事楼 3F 图**不必返工**: GRID_OF 投影继续工作, 等哪天有闲情
   按新规范重导出, 提取脚本平滑切换。
