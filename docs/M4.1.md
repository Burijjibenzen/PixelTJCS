## 2. 行为与数据如何运行

### 2.1 世界时钟、移动与气泡分别处理

后端通过连续时钟采样结算已流逝时间，切换倍率前先结算旧速度。定时快进保存目标游戏时刻及恢复速度，不把时钟直接跳到未来；3天快进在默认加速速度下约72现实秒，并触发最终维护。

Godot在快照之间连续显示时钟并缓慢校准偏差。移动和动画倍率按`当前速度 / 基础速度10`计算，暂停时停止推进。气泡的现实显示时长独立于世界倍率，展示结束与NPC任务占用不绑定。

后端模型正在生成、保存记忆或处理实际任务时仍可占用人物；仅仅保留一段已经生成的气泡不会阻止人物行动。完整台词可在日志中查看，不采用逐句排队或“等用户读完再行动”。

### 2.2 公开资料与秘密边界

`PersonaCard.public_profile()`显式投影公开字段，`GameService.public_npc_profile()`补充真实地点、目标及日程名称；API响应模型再限制输出字段。接口不返回整张原始人格卡、内部提示词、秘密或初始关系配置。

Godot在“社交观察 → 角色资料”复用原角色选择器，支持缺省字段、长文本、缓存和离线展示。活动信息集中在此显示，移除了重复固定活动窗口；使用“当前活动”“活动状态”“安排依据”“行程说明”“目的地”等标签，以及“基础作息”“正在前往目的地”等文案。

秘密仍按原设计进入所属NPC自己的模型上下文。公开字段隔离不等于模型回复经过绝对的秘密过滤；对话中的关系边界继续沿用既有提示策略，需要真实模型体验。

### 2.3 动态日程与实际到达

```text
人格基础作息 + 身份/性格规则 + 本人记忆/好友/已知事件
                     ↓
                校验后的活动候选
                     ↓
       优先级、占用、赴约与活动时间协调
                     ↓
   activity_targets → Godot原寻路 → 实际位置/到达上报
                     ↓
            到达后停留 → 完成 / 取消 / 超时
```

状态包括`scheduled`、`waiting`、`travelling`、`active`、`completed`、`cancelled`、`timed_out`；内部`phase`区分真正行走与到达后的活动阶段。基础作息翻段不会反复替换尚未到达的目标，断线和忙碌暂停活动预算，超时在资料页可观察。

事件只响应`participants`中的知情角色；记忆只读取本人有效记忆，好友从本人关系中选择。规则为图书分馆查资料、教室交流、健身休息等活动提供身份相关机会，不要求每个NPC每天到访智信馆，也不传送角色制造热闹。

每日计划模型经`AgentRuntime.plan_day()`复用`llm.py`出口，限制每个NPC每天的尝试和全局调用间隔，后台处理并校验地点、活动、时间和对象。无密钥、超时、迟到结果或无效输出均不破坏基础日程和规则计划。

会面仍使用原队列及双方实际抵达机制。事件活动优先级为70，手动安排为100；普通活动不能无条件打断正在执行的高优先级安排。停留与行走预算同时考虑当前速度和现实移动过程，参数见第7节。

### 2.4 公告栏从发布到记忆

```text
用户发布公告（此时没有NPC新增知识）
    ↓
同地图、同区域的附近角色发现未读公告
    ↓
在同区可走地板上寻找板前落点 → Godot实际行走
    ↓
进入阅读范围 → 等待已有任务 / 阅读2.5现实秒
    ↓
批准一次阅读 → 后台写入读者观察记忆
    ↓
仅读者获得已知事件与八卦来源 → 一句模板评论 → 可影响后续日程/交流
```

发现范围192地图像素，实际阅读范围64像素，坐标须新鲜且区域匹配。靠近使用有界BFS选择可达地板，再通过`target_position={x,y}`交给Godot原A*和物理移动，不把公告栏墙体中心当作落脚点。

智信馆公告栏的板前位置在图书分馆外走廊，物件区域已由`zx2_lib`修正为`zx2_corridor`，保留原物件ID、图层和公告记录。

普通行程可以顺路停靠；实际忙碌先完成，已在阅读范围内的阅读机会可预约，避免被新的低优先级任务反复抢占。未完成手动行程不被靠近抢占，高优先级活动或新的有效手动指派可取消靠近；离开、坐标过期、超时不产生阅读记忆。

读完后恢复原来的房间目标。前端缓存相同精确落点，防止每个快照重启寻路；撤去落点时，即使原目标在同一房间，也会恢复普通目标。

评论采用已读标题/正文对应的简短模板，复用原气泡和日志，不调用新评论模型、不新增第二份记忆或对话占用。发布、浏览公告不会使所有NPC知情；靠近连通校验不等于完整视线计算。

输入焦点或草稿存在时暂停自动刷新，刷新不锁输入框；列表未变时不重建卡片。发布回包只清除与提交时完全相同的草稿，保留请求期间新增内容和换行。

### 2.5 玩家身份与完整对话

```text
默认关闭 → 加入并获得session_id
    ↓
选择NPC → 提交message + request_id → 校验并预约NPC
    ↓                                  HTTP立即返回202
单工作线程：本人记忆/历史 → NPC回复 → 持久化完整双方台词
    ↓
分别写入NPC/玩家记忆 → 关系评估与幂等提交
    ↓
completed / failed → 释放NPC → 恢复已有行动
```

玩家身份是独立的`player:<UUID>`，同一称呼在本地数据库中稳定复用，不注册为第11名NPC。当前只允许单机单活动玩家，每次处理一轮；姓名与NPC重名、模式关闭、失效会话、忙碌和暂停均有明确行为。

模型只接收当前NPC自己的相关记忆，以及当前玩家与该NPC最近6轮完成记录；不会把与另一个NPC的对话历史直接放进本轮上下文。原`/chat`漏存NPC回复的问题已修复，双方完整台词分别写入玩家和目标NPC的第一人称对话记录，长回复尾部也保留。

记忆重要性使用固定配置0.45，未伪称模型评定；关系评估有效时变化范围±6，无效时保持原值并写明原因。稳定请求编号、记忆ID和关系事务分别避免重试带来的重复生成、重复记忆和重复加分。

模型、向量和关系评估不持有世界锁，其他NPC及世界时钟继续运行。目标NPC仅在实际处理一轮时占用，等待用户输入与展示气泡不占用人物。离开停止接收新轮次，已接受的一轮继续保存，完成后释放人物。

Godot提供顶部“玩家模式”面板，支持选人、地图点击切换聊天、按角色保留草稿、完整记录、关系原因及离线提示。输入控件获得焦点时，方向键、空格、数字和V不会误触镜头/地图操作。

## 5. HTTP 与事件契约

### 5.1 公开资料、活动与时间

- `GET /npcs/{name}/profile`：公开身份、目标、性格、日程与位置；未知角色404。
- `GET /npcs/{name}/activities`：当前活动、原因和最近活动记录。
- `POST /npcs/{name}/activities/{id}/cancel`：取消允许取消的活动。
- `POST /world/goto`：手动目标，支持`{npc,map_id,room_id}`或旧`{npc,area}`；实际位置仍由前端行走上报。
- `POST /world/report`：包含`map_id`、`room_id`、`arrived`、可选`activity_id`及地图内像素`x/y`，不能只靠心跳延长坐标有效期。
- `POST /world/advance`：`{minutes,speed?}`，3天为4320游戏分钟；请求接受后连续运行，不代表已经快进完成。
- `POST /world/speed`、`POST /social/control`：暂停、继续或倍率控制。

### 5.2 公告栏

- `GET /noticeboards`：三处稳定编号、名称、地图、区域与坐标，编号为`map_id:object_id`。
- `GET /noticeboards/{board_id}/notices`：公告列表、游戏发布时间及靠近/等待/阅读状态；查询不改变知识。
- `POST /noticeboards/{board_id}/notices`：`{title,content}`，最多80/500字。
- `POST /noticeboards/{board_id}/read`：保留`{npc}`调试入口，必须已在有效阅读位置；正常界面采用自动靠近与阅读。

### 5.3 玩家模式

| 接口 | 契约 |
| --- | --- |
| `GET /player` | `enabled`、`session_id`、`player={id,name}`、`pending_turn`、`pending_npc`、本人关系 |
| `POST /player/join` | `{name}`，默认“玩家”；同一活动身份重复加入返回同会话，更换身份前须离开 |
| `POST /player/leave` | `{session_id}`；重复离开安全，旧会话不能关闭新会话 |
| `POST /player/chat` | `{session_id,npc,message,request_id}`；立即202，返回轮次和状态 |
| `GET /player/turns/{turn_id}?session_id=...` | 查询`processing/completed/failed`、完整`transcript/reply`、双方记忆ID、关系和错误 |
| `GET /player/history?session_id=...&npc=...` | 本人最近50轮，按发生顺序；重新加入可查旧记录 |
| `GET /player/memory?session_id=...` | 本人活跃/遗忘记忆；历史归属与其他玩家分开 |
| `POST /chat` | 同步兼容入口，也须先加入；可带会话/请求编号，返回同一完整轮次结构 |

请求示例：

```json
{"session_id":"加入返回的会话ID","npc":"陈卷","message":"能聊聊研究计划吗？","request_id":"客户端本次生成的唯一编号"}
```

同一会话内重试必须沿用编号和内容，返回原结果；同编号换内容409。失败轮次也不自动重跑，明确发起新一轮时生成新编号。模式关闭、过期会话、忙碌或暂停409；未知对象404；空白/非法内容400，字段长度越界422。

回复先保存，后续记忆和关系完成前状态仍可为`processing`；`completed`才表示本轮保存步骤结束。旧`/chat`省略编号会创建新轮次，不提供无会话、无占用校验的绕过入口。

### 5.4 与原M3事件流衔接

沿用`/ws/events`、`dialogue_line`、`world`、`memory_changed`和`relation_changed`等事件。玩家和公告评论使用原日志/气泡规则，观察者看到台词不意味着所有NPC自动获得知识。

世界快照中的`activity`解释当前安排；公告靠近时附带地图内`target_position`，既有`target_map_id/target_room_id`继续可用。玩家身份不加入NPC快照名单；原NPC关系UI仍列10人，玩家关系由玩家面板展示，全量`/relations`会包含已创建的玩家身份。

## 6. 数据保存、去重与恢复边界

沿用现有SQLite数据库，启动自动补表，不清空已有NPC数据。

| 表/标识 | 用途 |
| --- | --- |
| `npc_activities`、`npc_plan_days`、`npc_plan_signals` | 动态活动、每日生成/模型尝试、知情信号去重 |
| `board_notices`、`board_reads`、`notice_comments` | 公告、每位读者的批准/完成状态、评论显示去重 |
| `player_profiles`、`player_sessions`、`player_turns` | 稳定玩家身份、活动/离开会话、轮次与完整结果 |
| `relation_effects` | 玩家关系更新与去重键同事务提交 |
| 原`memories`、`gossip`、`relations`、`m3_events`等 | 复用原记忆、来源传播、关系与事件持久化 |

公告记忆ID为`notice:<notice_id>:<npc>`，玩家记忆ID为`player-chat:<turn_id>:<agent>`。同一公告已经读过，即使记忆后来遗忘也不会自动重新写入；玩家历史独立于记忆的遗忘/容量管理。

动态日程保留锁定目标及生成状态，重启后的关系会面继续通过队列与真实到达协调。公告已批准但尚未写完的记忆可后台重试并在重启后恢复。

玩家模式每次服务启动默认关闭。已经完成的身份/历史/记忆/关系保留；中断轮次保留已提交结果并标记失败，不自动重跑模型；全部副作用已保存的轮次可确认为完成。离开不会删除记忆，未完成的一轮仍占用目标NPC直到结束。

## 7. 关键参数

统一在`backend/config.py`配置；不要将模型密钥放入代码、文档或Git。

| 配置 | 当前默认值/作用 |
| --- | --- |
| `SOCIAL.speed` / `fast_forward_speed` | 10 / 60游戏分钟每现实秒 |
| `SOCIAL.encounter_radius` | 自然相遇96地图像素 |
| `SOCIAL.position_report_seconds` / `position_max_age_seconds` | 上报间隔0.25秒 / 采样有效期2秒 |
| `SOCIAL.bubble_seconds` / `bubble_segment_chars` | 每段最多10现实秒 / 60字符分段参数 |
| `ACTIVITY.daily_optional_count` | 每日规则可选活动2项 |
| `ACTIVITY.dwell_minutes` / `min_stay_seconds` | 180游戏分钟 / 12个原速折算停留秒，均实际到达后累计 |
| `ACTIVITY.travel_timeout_seconds` / `pending_expiry_minutes` | 行走预算300原速折算秒 / 未出发窗口720游戏分钟 |
| `ACTIVITY.model_interval_seconds` / `model_timeout_seconds` / `model_result_deadline_seconds` | 全局调用间隔8秒 / 模型超时8秒 / 结果有效期12秒 |
| `NOTICEBOARD.discovery_radius` / `read_radius` | 发现192像素 / 阅读64像素 |
| `NOTICEBOARD.approach_timeout_seconds` / `read_seconds` | 靠近30现实秒超时 / 阅读2.5未暂停现实秒 |

| `PLAYER.name_max_chars` / `message_max_chars` | 称呼24字 / 玩家消息500字 |
| `PLAYER.context_turns` / `history_limit` | 上下文6轮 / 历史查询50轮 |
| `PLAYER.memory_importance` / `relation_max_delta` | 玩家对话记忆0.45 / 单轮好感变化最大6 |

## 8. 启动与操作验收

在配置好的Python环境中，从仓库根目录运行：

```powershell
python -m pip install -r requirements.txt
python -m uvicorn backend.api:app --port 8000
```

模型配置沿用本机`.env`，无配置时使用已有兜底。HTTP使用单后端进程，不增加多个worker；在Godot导入`frontend/project.godot`并运行。当前本机路径为`D:\TJU\LLMandAgents\Roamchestra`，其他组员按实际目录调整。

建议按顺序验收：

1. 确认后端连接，观察原速连续时钟，切换倍率，再验证定时快进会恢复速度。
2. 展开“社交观察 → 角色资料”，检查公开字段、活动原因、目的地与状态；拖动标题栏，点击人物/姓名切换跟随和资料。
3. 查看记忆/洞察的发生时间和距今时长，观察同走廊远距离角色不会自动当作近距离相遇。
4. 观察一个动态活动实际跨图到达；确认基础作息翻段不会反复改掉在途目标。
5. 点击地图公告栏或顶部“公告栏”，发布一条通知，保持输入草稿检查刷新保护；让原行动进入附近的角色自行靠近、阅读、评论，再检查读者记忆。
6. 点击“玩家模式”，填写称呼并加入；选NPC或点击地图人物，发送并查看双方记录、关系与记忆，观察世界继续运行；收起、离开和重入应保留历史。
7. 在试走模式确认智信馆二楼西端楼梯与济事楼三楼西侧楼梯双向衔接，原三/四楼楼梯也可使用。

`scripts/run_demo.py`的原CLI演示默认使用新建演示数据库语义；不要在需要保留HTTP记录时未经备份并行运行。截图、日志、数据库、虚拟环境和Godot缓存不入库。
