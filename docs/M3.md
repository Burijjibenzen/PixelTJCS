# M3 功能与代码交接说明

更新日期：2026-11-12。本文描述当前工作目录中的实现，不代表代码已经提交或合并。

M3 的范围是：相遇调度、世界循环、关系与八卦传播，以及 Godot 对话气泡、记忆面板和关系面板。实现依据为 `CODE_GUIDE.md` 的 M3 扩展指南和 LangGraph 迁移说明，以及 `DESIGN.md` 的 Agent 编排、WebSocket 事件流和 M3 里程碑。玩家实体、玩家开关和 human-in-the-loop 属于 M4，不包含在本次实现中。

本文中的源码路径均相对于仓库根目录。当前机器的仓库位置为 `E:\work\Roamchestra`。

## 2. 调度和对话如何运行

### 2.1 世界循环与调度入口

`Scheduler.loop()` 默认每 0.5 秒执行一次轻量 tick。tick 通过 `service.advance_time(..., maintenance=False)` 推进时钟，再处理占用释放、会面队列和自然相遇候选。重型遗忘／反思维护单独提交，不在每个 tick 中执行全员模型调用。

主调用链对应扩展指南：

```text
Scheduler.loop / tick
  ├─ service.advance_time(..., maintenance=False)
  ├─ world.co_located_pairs()
  ├─ 检查实际地点、在线、冷却、角色占用和会面优先级
  ├─ 关系加权随机筛选
  └─ Scheduler.graph
       perceive → decide → act
                            ├─ continue_schedule → 结束
                            ├─ move → 安排步行会面
                            └─ chat → service.run_conversation()
                                       → ConversationEngine.graph
```

关系影响的是候选进入决策的概率，而不是保证一定聊天。当前概率公式为：

```text
候选概率 = min(1, 基础概率 × (0.5 + 好感度 / 100))
```

默认基础概率为 20%，所以好感度为 0、50、100 时，规则筛选概率分别为 10%、20%、30%。通过筛选后，模型仍可决定继续日程。在线时的模型决策会参考人格、目标、日程和记忆；模型返回 `None` 时使用规则兜底。

相遇按同一真实地图、同一区域判定，不是按像素距离或碰撞判定。同名房间在不同楼层不会被视为相遇。高关系异地拜访是另一条候选路径，不会直接传送角色。

### 2.2 每个 NPC 的 LangGraph 子图

`AgentRuntime` 为每个 NPC 构建子图：

```text
perceive → decide → act
                    ├─ dialogue
                    ├─ write_memory
                    ├─ reflect
                    └─ 结束
```

不同任务调用已有 NPC 原子能力。结构化决策继续使用 `llm.py` 的 `chat_json()`，聊天和向量请求也保持该模块为唯一模型出口。这遵循 `CODE_GUIDE.md` 关于保留网关兼容处理的迁移说明；未用 LangChain 的模型客户端替换已有 GLM 适配。

### 2.3 一场对话的 LangGraph 节点

```text
validate → observe → opener
                     → reply_b → reply_a ─┐
                         ↑                │ 未达到设定轮数
                         └────────────────┘
                     → closing
                     → memory_a → memory_b
                     → assess → relation_update
                     → gossip_transfer
                     → reflect_a → reflect_b
                     → complete
```

默认 `WORLD.max_rounds = 2`，形成开场一句、两轮双方回复、结束一句，共六句。每个完整台词生成后立即发布 `dialogue_line`，不等待整场总结。

- `observe`：实际相遇形成双方各自的观察记忆。
- `memory_a`、`memory_b`：分别以本人视角保存对话记忆。
- `assess`、`relation_update`：评估并应用关系变化，保留原因。
- `gossip_transfer`：已实际转述的信息进入第三人的听说记忆。
- `reflect_a`、`reflect_b`：检查是否满足原有反思条件，不保证每场都会生成洞察。

图状态通过 `SqliteSaver` 保存到当前记忆数据库。对话记忆使用稳定 ID，关系更新与执行标记在同一事务中提交，反思用来源记忆集合识别已写入洞察，减少恢复时的重复副作用。

### 2.4 主动会面规则

用户请求同一对角色会面时会复用已有待执行请求，避免重复点击创建多个任务。共享角色的多项会面按顺序处理，待执行角色不会被自然相遇抢走。

典型状态为：

```text
waiting → moving → cooldown / ready → deciding → talking → playing → completed
                  任一等待阶段可能取消或因赴约超时失败
```

当前版本遵守文档中的冷却要求，主动会面也不跳过冷却。会面目标只覆盖下发给前端的目标，不修改人物实际位置；会面结束或取消后恢复原日程／指派目标。`deciding`、`talking`、`playing` 阶段不能取消。

## 5. 事件流与 HTTP 接口

### 5.1 WebSocket 协议

入口：`ws://127.0.0.1:8000/ws/events`。重连可携带 `?after=<最后处理的事件ID>`。

| 消息／事件 | 用途 |
| --- | --- |
| `snapshot` | 建连后同步世界、当前活跃台词、epoch 和游标 |
| `world` | 世界时间、NPC 位置／目标／占用和会面状态 |
| `conversation_started` | 对话开始 |
| `dialogue_line` | 完整台词，包含 conversation_id、sequence、speaker、text、participants |
| `movement` | NPC 实际位置变化 |
| `memory_changed` | 通知面板重新查询角色记忆 |
| `relation_changed` | 关系分数、变化值和原因 |
| `conversation` | 整场结果，包括 transcript、双方记忆和关系 |
| `conversation_released` | 释放对话占用及剩余气泡 |
| `world_event`、`error` | 注入事件和执行错误 |
| `heartbeat` | 服务端心跳；客户端发送 `{"kind":"ping"}` 维持在线状态 |

持久事件按递增 ID 去重。重连补取的历史台词进入对话日志，不重新播放已经过去的气泡；仍活跃的对话通过快照恢复最新一句。旧 `GET /social/events` 轮询接口已删除。

WebSocket 不改变模型生成速度，也不是逐 token 输出：后端得到完整一句后推送。记忆和关系评估可以在气泡出现后继续运行。

| 接口 | 说明 |
| --- | --- |
| `GET /health`、`GET /world` | 保留健康检查和世界查询 |

| `POST /world/speed`、`POST /social/control` | `{"paused":false,"speed":10}`；两个入口使用相同请求结构 |

## 6. 数据保存与恢复边界

普通启动使用仓库 `data/memory.db`；本地 GLM 测试入口使用其独立 runtime 数据库。两种模式下，LangGraph checkpoint 均与当前使用的记忆数据库放在一起。

新增或复用的 M3 表包括：

- `social_state`：保存游戏时钟。
- `social_changes`：最近的关系变化量。
- `gossip`：原始信息、持有者、来源、跳数和关联记忆。
- `m3_events`：持久事件及去重键。
- `m3_runs`：对话图运行状态。
- `m3_effects`：关系更新执行标记。
- `m3_memory_history`：角色记忆历史快照。
- LangGraph SQLite checkpointer 创建的检查点表。

恢复是显式操作，不会在启动时自动重试所有失败模型请求。待执行会面队列、实时角色占用和精确位置不是完整世界存档；重启后位置由原初始化和前端上报校准。记忆时间线展示已记录的状态快照，不是任意过去时刻的完整世界还原或重新执行向量检索。

HTTP 社交服务要求实际同区域，禁止对话引擎把人物直接传送过去；纯 CLI 演示仍保留原有简化位置调度，因此可以继续运行原演示脚本。

## 7. 关键参数

后端入口是 `backend/config.py` 中的 `SOCIAL` 和 `WORLD`。

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| tick_seconds | 0.5现实秒 | 世界循环间隔 |
| speed | 10 | 每现实秒推进的游戏分钟 |
| decision_interval | 15现实秒 | 同一对自然候选的决策筛选间隔 |
| base_chat_probability | 0.20 | 关系加权前的基础候选概率 |
| max_conversations | 2 | 并发任务上限；模型决策、生成和占用也会消耗名额 |
| WORLD.cooldown_minutes | 120游戏分钟 | 同一对角色的冷却，默认速度下约12现实秒 |
| WORLD.max_rounds | 2 | 默认双方回复轮数，另外包含开场与结束语 |
| presence_seconds | 15现实秒 | 客户端活跃状态判定窗口 |
| meeting_timeout | 300现实秒 | 等待位置上报／赴约的累计超时；不是整个请求所有等待阶段的总时限 |
| maintenance_minutes | 30游戏分钟 | 后台维护触发间隔，不保证每次都产生反思 |
| visit_relation | 80 | 异地主动拜访候选的关系阈值 |
| gossip_max_hops | 3 | 同一条信息最多传播跳数 |
| bubble_seconds | 10现实秒 | 完成后保留占用的时间 |

前端 `social_ui.gd` 的 `BUBBLE_SECONDS=10`、`SEGMENT_CHARS=60` 控制每段展示上限和分段长度。更改展示时长时需同时检查后端的释放时机。
